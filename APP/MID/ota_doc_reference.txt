一、OTA 升级原理
1.1 OTA 概述
OTA（Over-The-Air，空中下载技术）是一种通过无线网络对嵌入式设备的固件进行远程升级的技术。对于本项目的 STM32F407ZGT6 + ESP8266 平台而言，OTA 升级意味着：设备通过 ESP8266 WiFi 模块连接到互联网，从 OneNET 云平台接收升级通知和下载固件包，将新固件写入外部 Flash（W25Q128）的"升级固件区"，由 BootLoader 负责固件搬运和自动回滚，APP 负责升级成功后备份固件，实现安全可靠的远程升级。
1.2 OneNET OTA 架构
OneNET 平台的 OTA 服务采用 "MQTT 通知 + HTTP 下载" 的混合架构：
MQTT 通道（实时通知）：
设备通过 MQTT 长连接保持在线，可实时接收平台下发的 OTA 升级通知。
MQTT 主题：$sys/{产品ID}/{设备名}/thing/property/set —— 平台可下发 JSON 格式的升级指令。
HTTP 通道（固件传输）：
固件升级包较大（几十KB ~ 几百KB），不适合通过 MQTT 传输。
OTA 服务使用 HTTP RESTful API，设备通过 HTTP 请求完成：版本上报 → 任务查询 → Token 校验 → 分片下载固件 → 状态上报。
OTA 服务器域名：ota.heclouds.com（端口 80），新版 API：iot-api.heclouds.com

1.3.3 三区协作的核心原理
以下通过一个完整的升级场景说明三个区如何协作（假设当前运行 V1.0.0，要升级到 V1.0.1）：
【下载阶段 - APP负责】APP 从 OneNET 下载 V1.0.1 固件到"升级固件区"（区1），下载完成后将升级标志位设为 0xAA55AA55，将新固件版本号"V1.0.1"写入标志区（区3）的 new_ver 字段，然后软件复位。
【搬运阶段 - Boot负责】BootLoader 上电后读取区3，发现升级标志位 = 0xAA55AA55，开始执行升级：① 擦除片上 Flash APP 区（0x08010000）② 从"升级固件区"（区1）读取 V1.0.1 固件，写入片上 Flash APP 区③ 校验新固件栈地址（SP）是否合法④ 更新区3的标志：升级标志位 = 0x55AA55AA（已搬运待确认），启动失败计数+1⑤ 跳转到新 APP（V1.0.1）★ 注意：BootLoader 不做备份操作！备份由 APP 确认升级成功后执行。
【确认阶段 - APP负责】V1.0.1 固件启动后，完成 WiFi 和 MQTT 初始化，确认固件功能正常后：① ★ 备份新固件：将"升级固件区"（区1）的 V1.0.1 固件复制到"备份区"（区2）② 将保护标志位写入 0xBB66BB66（表示"新固件已验证OK"）③ 更新标志区：current_ver = "V1.0.1", backup_ver = "V1.0.1"④ 上报升级成功（状态码 201）如果 APP 在完成备份和写入保护标志位之前崩溃（看门狗复位），BootLoader 将检测到保护标志位不正确，触发回滚。（此时区2中仍是上一个成功版本，可以安全回滚）
【回滚阶段 - Boot负责（关键安全机制）】BootLoader 上电后，如果发现升级标志位 = 0x55AA55AA 但保护标志位 ≠ 0xBB66BB66，说明上次升级后新 APP 未能成功运行确认。此时执行回滚：① 从"备份区"（区2）读取旧固件 V1.0.0② 擦除片上 Flash APP 区③ 将旧固件写入 APP 区④ 清除升级标志位和启动失败计数⑤ 跳转回旧 APP这样即使升级失败，设备也能自动恢复到上一个正常工作的固件版本，不会变砖。

二、OTA 服务器连接
2.1 设备鉴权与签名算法
OneNET OTA 服务的所有 HTTP API 都需要在请求头中携带 Authorization 鉴权信息。签名算法使用 HMAC-SHA1，与 MQTT 连接的 token 鉴权不同（但算法思想类似）。
2.1.1 Authorization 头部格式
新版融合API（iot-api.heclouds.com）使用以下鉴权格式（推荐使用）：
version=2022-05-01&res=userid%2F{用户ID}&et={过期时间戳}&method=sha1&sign={签名结果}
旧版通用API（ota.heclouds.com）使用以下鉴权格式：
version=2018-10-31&res=products%2F{产品ID}&et={过期时间}&method=sha1&sign={签名}
参数说明：
参数
说明
version
鉴权版本号。新版API填 2022-05-01，旧版API填 2018-10-31
res
资源路径。新版API: userid/{用户ID}，旧版API: products/{产品ID}（需URL编码 %2F）
et
过期时间，Unix 时间戳（建议设为当前时间 + 86400秒即24小时）
method
签名算法：sha1 / sha256 / md5（推荐 sha1）
sign
签名结果，Base64 编码
2.1.2 签名生成步骤
完整的签名计算过程如下（STM32 上使用 mbedtls 库实现）：
1. 获取 access_key：在 OneNET 控制台 → 产品详情 → access_key（Base64编码的密钥）
2. 拼接签名字符串：{et}\n{method}\nproducts/{product_id}\n{version}（注意是用 \n 换行符分隔）
3. 对 access_key 进行 Base64 解码，得到 hmac_key（二进制密钥）
4. 使用 hmac_key 对签名字符串进行 HMAC-SHA1 计算，得到 20 字节的摘要
5. 将摘要进行 Base64 编码，得到最终 sign 值
6. 将所有参数拼成 Authorization 头部值（注意需要对特殊字符进行 URL 编码）
签名字符串示例：
新版API示例（推荐）：假设：et=1735660800, method=sha1, userid=12345, version=2022-05-01签名字符串为：1735660800\nsha1\nuserid/12345\n2022-05-01旧版API示例：1735660800\nsha1\nproducts/245528\n2018-10-31

2.4 设备端网络通信架构
由于 ESP8266 的 AT 固件限制，同一时刻只能有一个 TCP 连接处于活跃状态，需要采用分时复用策略：
正常运行阶段：保持 MQTT 长连接（mqtts.heclouds.com:1883）。
OTA 下载阶段：暂停 MQTT 心跳，断开 MQTT，建立 HTTP 连接到 ota.heclouds.com:80。
OTA 完成后：恢复 MQTT 连接，继续正常通信。
三、OTA 通信协议详解
本章详细列出 OTA 升级过程中设备端需要调用的每一个 HTTP API。所有 API 均需在 HTTP 请求头中添加 Authorization 鉴权信息。
3.1 上报设备版本号 (POST)
设备启动后或首次升级时，需要将当前固件版本号上报到平台。这是 OTA 流程的第一步。
请求方式：POST
URL：http://ota.heclouds.com/ota/device/version?dev_id={设备ID}
请求头：
Content-Type: application/jsonAuthorization: version=2018-10-31&res=products%2F{产品ID}&et={过期时间}&method=sha1&sign={签名}
请求体（JSON）：
{"s_version": "V1.0.0"}    // SOTA: MCU应用版本号
版本号格式要求：只能包含 [a-zA-Z0-9_\-.] ，长度 1~20 字符。
3.2 检查升级任务 (GET)
设备调用此 API 查询是否存在待处理的升级任务。平台会比对设备上报的版本号与目标版本号，如果不一致且存在升级任务，则返回任务详情。
请求方式：GET
★ 新版融合API（推荐）：GET https://iot-api.heclouds.com/fuse-ota/{pro_id}/{dev_name}/check?type={类型}&version={当前版本}
旧版通用API：GET http://ota.heclouds.com/ota/south/check?dev_id={设备ID}&manuf={厂商编号}&model={模组型号}&type={类型}&version={当前版本}&cdn={是否返回IP}

3.4 分片下载固件 (GET + Range)
这是 OTA 升级中最核心的步骤。设备通过 HTTP Range 头部实现分片下载，每片下载完成后写入 W25Q128 的"升级固件区"（区1），并上报进度。
支持断点续传：网络中断后可以从上次断点继续下载，不用重新开始。
内存占用小：每次只需分配几 KB 的接收缓冲区。
进度可控：可以精确上报下载百分比给平台。
请求方式：GET
★ 新版融合API：GET https://iot-api.heclouds.com/fuse-ota/{pro_id}/{dev_name}/{tid}/download
旧版通用API：GET http://ota.heclouds.com/ota/south/download/{token}
Range 头部格式：
格式
说明
示例
Range: bytes={start}-
从第 start+1 字节到末尾
Range: bytes=0- (获取全部)
Range: bytes={start}-{end}
获取指定范围

获取最后 end 个字节

响应头关键字段（新版API）：
Content-Disposition: 包含 filename 固件文件名
Content-Range: 格式 bytes {start}-{end}/{total}，total 为文件总字节数
Content-Length: 当前分片的实际数据字节数
Ota-Errno: 下载错误码。0=成功, 1=设备不存在, 2=文件资源不存在, 3=存储资源不存在, 4=文件大小不一致, 5=任务已完成/取消, 6=鉴权失败
分片下载代码思路：
// 分片下载固件到 W25Q128 升级固件区（区1）#define CHUNK_SIZE      4096#define W25Q_FW_ZONE1   0x00000000   // 升级固件区起始地址void OTA_DownloadToZone1(const char *token, uint32_t total_size, const char *ip){    uint32_t offset = 0;    uint8_t buf[CHUNK_SIZE];    uint32_t w25q_addr = W25Q_FW_ZONE1;    // 先擦除区1（按64KB块擦除，确保干净）    for (uint32_t addr = W25Q_FW_ZONE1;         addr < W25Q_FW_ZONE1 + total_size;         addr += 65536) {        W25Q128_BlockErase_64K(addr);    }    while (offset < total_size) {        uint32_t end = (offset + CHUNK_SIZE - 1 < total_size)                       ? (offset + CHUNK_SIZE - 1) : (total_size - 1);        ESP_Connect_TCP(ip, 80, 5000);        char http_req[512];        sprintf(http_req,            "GET /ota/south/download/%s HTTP/1.1\r\n"            "Host: ota.heclouds.com\r\n"            "Authorization: %s\r\n"            "Range: bytes=%lu-%lu\r\n\r\n",            token, g_ota_auth, offset, end);        ESP_SendToTCPServer(http_req, 10000);        uint16_t data_len = parse_http_response(TCPdata, buf, CHUNK_SIZE);        W25Q128_Write(w25q_addr + offset, buf, data_len);  // ★ 写入区1        offset += data_len;        OTA_ReportProgress(token, offset * 100 / total_size);        // 持久化断点信息到标志区        OTA_SaveResumePoint(offset);    }}
3.4.1 固件 .bin 文件格式要求
OTA 下载的固件必须是 .bin 格式（原始二进制），不能使用 .hex 文件。编写 APP 工程时需要注意：
1. APP 程序起始地址必须是 0x08010000（Keil → Options → Target → IROM1 → Start = 0x08010000, Size = 0xF0000）。
2. main() 函数开头必须设置向量表偏移：SCB->VTOR = 0x08010000;（当前 APP 工程已正确设置）。
3. 编译后使用 fromelf 工具将 .axf 转为 .bin：fromelf --bin -o output.bin input.axf
4. .bin 文件的第一个字（4字节）必须是栈顶地址（MSP初始值，应在 0x20000000~0x20020000 范围内），第二个字是复位向量（0x08010001）。BootLoader 通过检查这两个值来验证固件是否有效。
5. 上传到 OneNET 平台的固件必须是这个 .bin 文件。平台自动计算 MD5 并记录版本号。
3.5 上报升级状态 (POST)
设备在升级过程中需要通过 HTTP POST 向平台上报当前进度和状态。OneNET 平台提供两种上报方式（progress 和 report），推荐使用 progress 接口。注意：两种接口的数值含义不同，切勿混淆。
方式一：progress 接口（推荐）
★ 新版融合API：POST https://iot-api.heclouds.com/fuse-ota/{pro_id}/{dev_name}/{tid}/status （统一的上报接口）
旧版通用API：POST /ota/south/device/download/{token}/progress?dev_id={设备ID}
请求体：{"step": 54}  // step 范围 0~100 表示下载进度百分比
★ 重要：上报 step=100 时，平台自动将设备状态从"正在下载"切换为"正在升级"。
因此，下载完成后上报 step=100（而不是101），然后由 BootLoader 完成固件搬运，新 APP 启动后再调用 report 接口上报 result=201（升级成功）。
方式二：report 接口
★ 新版融合API：POST https://iot-api.heclouds.com/fuse-ota/{pro_id}/{dev_name}/{tid}/status （同上接口）
旧版通用API：POST /ota/south/report?dev_id={设备ID}&token={token}
请求体：{"result": 101}  // 这里用 result 字段，101=下载成功
使用此接口需要调用两次：先报 result=101（下载成功），再报 result=201（升级成功）。
注意：progress 接口的 step=100 等同于 report 接口的 result=101，都表示下载完成。

四、OTA 升级完整流程（含回滚机制）
4.1 平台侧操作步骤
在设备端开发之前，需要先在 OneNET 平台完成以下配置：
1. 登录 OneNET 开发者中心（https://open.iot.10086.cn），进入已创建的产品。
2. 在左侧菜单找到"OTA 远程升级" → "固件管理" → "添加固件"。上传编译好的 .bin 固件文件，填写版本号。
3. 在"升级任务管理"中创建升级任务：选择目标固件版本、选择设备、配置升级策略。
4. 平台将升级任务下发给目标设备。设备下次查询时即可获取到任务。
5. 在"设备管理"中查看设备的升级状态。
4.2 设备侧升级步骤
设备侧完整的 OTA 升级流程（含三区联动和回滚逻辑）：
步骤1：设备启动 → BootLoader 判断
BootLoader 上电后首先读取标志区（区3）的三个关键字段：a) 升级标志位 upgrade_flagb) 保护标志位 protect_flagc) 启动失败计数 boot_fail_cnt根据这些字段的值决定走"正常跳转"、"执行升级"还是"触发回滚"路径。详见 4.3 节 BootLoader 设计。
步骤2：APP 正常运行与版本上报
APP 启动后：连接 WiFi → 连接 MQTT → 调用 HTTP POST 上报当前版本号（读取标志区 current_ver）。如果保护标志位尚未写入（这是新固件首次启动），在功能初始化完成后写入 protect_flag = 0xBB66BB66。
步骤3：接收 OTA 升级通知
方式A（MQTT 下发）：平台通过 property/set 主题下发升级通知，在 ESP_MQTT_MsgProcess() 中解析触发。方式B（主动轮询）：定时调用 HTTP GET /ota/south/check 查询升级任务。
步骤4：检查升级任务并获取信息
调用 /ota/south/check 接口。如果 errno=0，提取 token、target、size、md5、ipPort。比较 target 与标志区的 current_ver，如果相同说明已是最新，跳过升级。
步骤5：升级条件检查
检查：WiFi 信号强度、W25Q128 区1空间是否足够、版本号是否不同。条件不满足则暂缓升级。
步骤6：分片下载固件到"升级固件区"（区1）
a) 擦除区1对应区域b) HTTP Range 分片下载，每片 4096 字节c) 写入 W25Q128 区1（地址 0x00000000 起始）d) 每片上报进度，持久化断点信息（已下载字节数）到标志区e) 全部下载完成后计算 MD5，对比平台给的 md5
步骤7：写入升级标志 → 通知 BootLoader
MD5 校验通过后：a) 将新固件版本号写入标志区 new_ver 字段b) 将固件大小写入标志区 fw_size 字段c) 将升级标志位 upgrade_flag 设为 0xAA55AA55（★ 这是告诉 BootLoader 有新固件的关键操作）d) 上报下载完成（progress接口 step=100，触发设备状态切换为"正在升级"）e) 调用 NVIC_SystemReset() 软件复位
步骤8：BootLoader 执行固件搬运
BootLoader 重启后，检测到 upgrade_flag = 0xAA55AA55 且 protect_flag ≠ 0xBB66BB66：a) 擦除片上 Flash APP 区（0x08010000 ~ 0x080FFFFF）b) 搬运新固件：从 W25Q128"升级固件区"（区1）读取 .bin 数据，写入片上 Flash APP 区c) 校验栈地址（SP）合法性d) 更新标志区：升级标志位改为 0x55AA55AA，启动失败计数+1e) 跳转到新 APP★ BootLoader 不做备份！备份由 APP 在确认升级成功后完成。
步骤9：新 APP 启动并确认升级
新 APP 启动后：a) 连接 WiFi 和 MQTTb) 初始化各项功能，确认固件运行正常c) ★ 备份固件到备份区：将"升级固件区"（区1）的新固件复制到"备份区"（区2），作为下一个可回滚的版本d) ★ 将保护标志位 protect_flag 设为 0xBB66BB66（关键一步！告诉 BootLoader 升级成功）e) 更新标志区：current_ver = new_ver, backup_ver = new_verf) 上报升级成功（report接口 result=201）如果新 APP 在完成备份和写入保护标志位之前因看门狗复位而重启，BootLoader 将检测到 upgrade_flag = 0x55AA55AA 但 protect_flag ≠ 0xBB66BB66，触发回滚。（此时区2中仍是上一个成功版本，可以安全回滚）
步骤10：升级失败 → 自动回滚
触发回滚的条件（任一满足即触发）：a) 升级标志位 = 0x55AA55AA（已搬运完成）但保护标志位 ≠ 0xBB66BB66（APP未确认）b) 启动失败计数 boot_fail_cnt >= 3（看门狗反复复位超过阈值）c) 新APP区栈地址校验不通过回滚执行流程：① 从"备份区"（区2）读取旧固件② 擦除片上 Flash APP 区③ 写入旧固件到 APP 区④ 清除升级标志位、启动失败计数⑤ 跳转回旧 APP → 旧 APP 上报升级失败（206）

4.5 断点续传机制
断点续传的关键是持久化已下载的字节偏移量。在本方案中，断点信息存储在标志区：
断点存储位置：标志区（区3）的保留字段，如 0x00C00100 处，存储 downloaded_size（4字节）。
每次分片下载成功（W25Q128 写入完成）后，更新标志区的 downloaded_size。
下载中断后（网络断、断电），下次重新开始下载前：读取标志区 downloaded_size →擦除区1从 downloaded_size 之后的区域 → 从 offset=downloaded_size 继续下载。
Token 过期处理：如果 token 过期，清除下载进度，重新调用检查任务获取新 token，从头下载。

           if (HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD,                                  flash_addr + off + i, word) != HAL_OK) {                HAL_FLASH_Lock();                return -1;            }        }    }    HAL_FLASH_Lock();    return 0;}

5.7 FreeRTOS OTA 任务示例
5.7.1 OTA 下载任务
// OTA 下载任务（在 APP 中运行）void OTA_Task(void *argument){    vTaskDelay(pdMS_TO_TICKS(5000));  // 等待WiFi+MQTT就绪    // 启动时检查是否需要上报升级结果    uint32_t upgrade_flag = Flags_ReadUpgradeFlag();    uint32_t protect_flag = Flags_ReadProtectFlag();    if (upgrade_flag == UPGRADE_MAGIC_COMMITTED &&        protect_flag == PROTECT_MAGIC_OK) {        // 这是升级成功的新APP首次运行        printf("[OTA] 升级成功！上报结果...\r\n");        char token[64];  Flags_ReadToken(token);        OTA_HTTP_ReportResult(MY_DEV_ID, token, 201);  // 上报升级成功（report接口）        char new_ver[24];  Flags_ReadNewVer(new_ver);        OTA_HTTP_ReportVersion(MY_DEV_ID, new_ver);      // 上报新版本号        Flags_ClearBootFailCnt();        Flags_SetUpgradeFlag(UPGRADE_MAGIC_NONE);    }    else if (upgrade_flag == UPGRADE_MAGIC_COMMITTED &&             protect_flag != PROTECT_MAGIC_OK) {        // 这是回滚后的旧APP        printf("[OTA] 检测到升级失败回滚，上报失败...\r\n");        char token[64];  Flags_ReadToken(token);        OTA_HTTP_ReportResult(MY_DEV_ID, token, 206);  // 上报升级失败（report接口）        Flags_SetUpgradeFlag(UPGRADE_MAGIC_NONE);        Flags_ClearBootFailCnt();    }    // 主循环    while (1)    {        // 等待OTA触发信号量（MQTT通知或定时器）        if (osSemaphoreAcquire(OTA_TriggerSemHandle, pdMS_TO_TICKS(30*60*1000))            != osOK) {            // 30分钟超时 = 定时轮询        }        // 1. 上报版本号        char cur_ver[24];  Flags_ReadCurrentVer(cur_ver);        OTA_HTTP_ReportVersion(MY_DEV_ID, cur_ver);        // 2. 检查升级任务        OTA_Ctx_t ctx = {0};        int ret = OTA_HTTP_CheckTask(MY_DEV_ID, cur_ver, &ctx);        if (ret != 0) continue;  // 无任务        // 3. 版本比较（避免重复升级）        if (strcmp(ctx.target_ver, cur_ver) == 0) continue;        printf("[OTA] 发现新版本: %s -> %s\r\n", cur_ver, ctx.target_ver);        // 4. 保存token和MD5到标志区        Flags_SaveToken(ctx.token);        Flags_SaveMd5(ctx.file_md5);        Flags_WriteNewVer(ctx.target_ver);        Flags_WriteFwSize(ctx.file_size);        // 5. 分片下载固件到区1        if (OTA_DownloadToZone1(ctx.token, ctx.file_size,                                ctx.download_ip) != 0) {            printf("[OTA] 下载失败\r\n");            continue;        }        // 6. MD5校验        if (OTA_VerifyMd5(W25Q_ZONE1_ADDR, ctx.file_size, ctx.file_md5) != 0) {            printf("[OTA] MD5校验失败，重新下载\r\n");            OTA_HTTP_ReportResult(MY_DEV_ID, ctx.token, 205);            continue;        }        // 7. ★ 设置升级标志 → BootLoader下次启动会处理        Flags_SetUpgradeFlag(UPGRADE_MAGIC_READY);  // 0xAA55AA55        // 8. 上报下载完成        OTA_HTTP_ReportProgress(MY_DEV_ID, ctx.token, 100);  // step=100: 下载完成，状态切换为"正在升级"        // 9. 软件复位，进入BootLoader        printf("[OTA] 3秒后复位，进入BootLoader升级流程...\r\n");        vTaskDelay(pdMS_TO_TICKS(3000));        NVIC_SystemReset();    }}
5.7.2 APP 启动确认与固件备份
// 在 APP 主初始化完成后（如 ESP_RxTask 的第一个循环中）调用void OTA_ConfirmBootSuccess(void){    uint32_t upgrade_flag = Flags_ReadUpgradeFlag();    if (upgrade_flag == UPGRADE_MAGIC_COMMITTED) {        // BootLoader已搬运新固件，现在是新固件首次运行        uint32_t fw_size = Flags_ReadFwSize();        // ★ 步骤1：备份新固件到备份区（区1 → 区2）        // 区2保存已验证成功的最新版本，用于下次升级失败时回滚        printf("[OTA] 备份新固件到备份区...");        for (uint32_t addr = W25Q_ZONE2_ADDR;             addr < W25Q_ZONE2_ADDR + fw_size; addr += 65536) {            W25Q128_BlockErase_64K(addr);        }        uint8_t buf[256];        for (uint32_t off = 0; off < fw_size; off += 256) {            uint32_t chunk = (fw_size - off > 256) ? 256 : (fw_size - off);            W25Q128_Read(W25Q_ZONE1_ADDR + off, buf, chunk);            W25Q128_Write(W25Q_ZONE2_ADDR + off, buf, chunk);        }        printf("[OTA] 备份完成");        // ★ 步骤2：写入保护标志确认升级成功        Flags_SetProtectFlag(PROTECT_MAGIC_OK);  // 0xBB66BB66        // 步骤3：更新标志区版本号        char new_ver[24];  Flags_ReadNewVer(new_ver);        Flags_WriteCurrentVer(new_ver);        Flags_WriteBackupVer(new_ver);        // 步骤4：清除启动失败计数        Flags_ClearBootFailCnt();        printf("[OTA] 升级确认完成，保护标志已写入");    }}// 注意：如果此函数未能执行（APP崩溃导致看门狗复位），// BootLoader检测到protect_flag≠0xBB66BB66而触发回滚。// 此时区2中仍是上一个成功版本，可以安全恢复。
